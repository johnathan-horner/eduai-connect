ShootItPicks

An NFL player-prop research site: odds from several sportsbooks side by side, the site's own probability next to each price, and an AI chat that answers only from the site's data. It takes no bets and never tells anyone to bet.

case study

The problem

Prop bettors compare prices across several sportsbooks and lean on gut feel or tips nobody checks. Most tools show a number without saying where it came from or how often numbers like it turned out right.

Why I built it

I wanted to run a real product where every probability is logged before kickoff and settled after, and where an AI chat can explain a bet without inventing a number or telling anyone what to bet.

Key decisions

  1. Statistical models make the probabilities; the language model only explains. Earlier LLM-generated confidence scores were deleted because nothing backed them. The tradeoff is fewer eye-catching outputs, in exchange for probabilities that can be checked against results.
  2. Pull every shown number toward the market. Settled results showed the sportsbooks' prices were closer to what happened than the raw model. Each probability is now pulled toward the book's no-vig price, refit weekly per market and blended with a prior so two noisy weeks can't swing it. Picks look less exciting, and they are more honest.
  3. Every number in a chat answer must come from the data. A number check allows one rewrite, then falls back to a plain answer built from the data. Better a dull answer than a confident wrong fact; the eval gate allows at most 2% of answers to fall back.
  4. Graders come from a different vendor than the model that answered. A model never grades its own work. Claim and verdict checks use the other vendor's model, and money-at-risk questions fail closed if the grader is down. The cost is extra latency, spend and a dependency on two vendors' rate limits.

Architecture

Board picks come from statistical models. Each probability is calibrated against the market, logged before the game and settled after, and ranking rules keep picks with thin data, long odds or suspect gaps off the featured list with the reason shown. The chat first fetches the data it needs through tools on the server; betting questions then run a five-step chain (player performance, matchup and situation in parallel, then line value, then the answer), and every answer passes number, claim, voice and verdict checks before it is shown with a Sources line underneath.

Governance and safety

  • 21+ and 1-800-GAMBLER across the site and chat; the site never tells anyone to bet, and the free plan gets no verdict.
  • Questions that mention money at risk get a fixed warning written by code, plain numbers only and no lean.
  • Number check on every chat answer, a cross-vendor claim check on paid plans, and a cross-vendor verdict check.
  • Ranking rules with eight reason codes (no recent games, low usage, Doubtful, long shot, suspect gap and others) keep weak picks unranked, with the reason attached.
  • Every board prediction is logged before kickoff and settled after; one log line per chat answer, with no user ID.
  • Tokens and emails are kept out of logs (tested), sign-up IPs are stored only as a keyed hash, and users can download their data.
  • Not built yet: a hard age check (age is self-attested through the Terms), automated data deletion, and human review before an answer is shown.

Results

  • Defense-vs-position backtest on 47,299 predictions: Brier score 0.20097 to 0.20063 and calibration error 0.0118 to 0.0108. It ships on 6 of 7 markets and is left off rushing yards, where it made things worse.
  • 112-question chat eval across 17 categories gates every model change: quality 90% or better, every category 75% or better, at most 2% fallback answers, zero hard-rule breaks.
  • 1,249 backend tests and 96 frontend tests run in CI on every pull request, plus a phone end-to-end check.

Limits

Projections are somewhat overconfident on narrow ranges, parlay legs are treated as independent, and calibration rests on a few weeks of settled results. It is analytics, not betting advice.

What I'd add next

Add a hard age check and automated data deletion, model projection error and same-game correlation, and publish calibration on a full season of settled picks.

case study

The problem

Banks that put language models near investment decisions have to manage them as models under SR 26-2 (formerly SR 11-7): an inventory, independent validation, ongoing monitoring and a record of what each model said. Most AI assistants skip all of that.

Why I built it

I wanted to see whether those controls could live in the code rather than in a policy document: numbers computed before the model sees them, only validated model and prompt versions allowed to answer, and every answer graded and traced.

Key decisions

  1. An approval gate keyed to the exact model and prompt hash. Each LLM component may call a provider only if the held-out evaluation recorded an approval for that provider, model ID and prompt version hash, and only the evaluation harness writes approvals. Any prompt or model change blocks live use until a new held-out run approves it; meanwhile the app falls back.
  2. Code computes every number; the model only explains. Monte Carlo CVaR (10,000 seeded runs), VaR, stress tests and PSI drift are computed first, and the agents are told to use only those numbers. Earlier failures came from the model doing its own arithmetic. The agents can only discuss what the engine computed.
  3. Bedrock first, Gemini as fallback, and a grader that is always a different model. Claude Haiku 4.5 answers through the US cross-Region inference profile, Gemini takes over on any Bedrock error, and demo mode is last. Every output gets an LLM grade from a different model plus a deterministic number check. The cost is two vendors and two prompt sets to validate, and Gemini is always needed for embeddings.
  4. Production stack in CDK, synthesized in CI, not deployed. Bedrock Guardrails, KMS, CloudTrail with 7-year retention, API Gateway and Lambda are defined and checked by cdk synth on every push, with no AWS spend. Those controls are designed, not exercised, and the CDK Lambda does not yet carry the approval gate, RAG or grader.

Architecture

A chat question passes a topic filter, then the RAG chain writes a hypothetical answer (HyDE), searches the committed FAISS index with it and the raw question, re-ranks to the top 4 with a local cross-encoder, and asks the approval gate which provider may answer: Claude Haiku 4.5 on Amazon Bedrock, then Gemini, then demo mode. A different model grades the answer, a number check runs, and a trace record is shown under it. The second diagram is the production design in the repo's CDK code, synthesized in CI and not deployed.

Governance and safety

  • Approval gate: only APPROVED or CONDITIONAL records for the exact provider, model ID and prompt hash may answer; approvals are written only by the held-out evaluation harness.
  • Model inventory of 6 models (MRM-001 to MRM-006) with risk tier, lifecycle stage and validation status.
  • Independent grader on every live output (always a different model) plus a check that every number rounds from a source number; marked UNGRADED if no other model is available.
  • A trace record per output: provider, model, prompt versions, index hash, sources, grade, approval status and latency.
  • A topic filter refuses insider-trading and market-manipulation questions, a PII regex redacts every output, live use is capped at 10 requests per session, and every output names the provider and model that answered.
  • Not in the running app: Bedrock Guardrails, KMS and CloudTrail (defined in CDK only), human review, and a durable audit log (traces are kept in memory).

Results

  • Held-out RAG chat (MRM-001), latest run on 2026-11-11: 23 of 23 passed on Claude Haiku 4.5 with 100% exact-fact accuracy, for $0.067 of Bedrock calls; the Gemini fallback also passed 23 of 23. On a 23-item set, one item is about 4 points.
  • Agents on held-out sets with Claude Haiku 4.5: market 10/10, risk 9/10, portfolio 10/10, orchestrator 9/10, all approved.
  • 99% VaR backtest over 254 test days: 2 to 3 exceptions, Kupiec p-value 0.72 to 0.78, Basel green zone.
  • 118 automated tests in CI, plus cdk synth of the production stack.

Limits

Synthetic portfolio and market data, small held-out sets (23 chat items, 10 per agent), not reviewed by an independent validation team or a regulator, and not investment advice.

What I'd do in a real deployment

Deploy the CDK stack with the approval gate, RAG and grader inside the Lambda, apply Bedrock Guardrails to every call, keep traces in a durable audit store, use the bank's own market data, and have an independent validation team review it before anyone relies on it.

The problem

Radiology worklists mix urgent and routine chest X-rays. A triage aid is only useful if it knows which cases it can sort on its own and which ones need a person, and if it leaves a record of every decision.

Why I built it

I wanted to see whether a small image model trained on a laptop CPU could split X-rays into a confident lane with no missed pneumonia and a review lane for people, and whether an LLM could add a readable note without ever seeing the image.

Key decisions

  1. Pick the routing threshold on half of the test split and report on the other half. The validation split is easier than test: a threshold picked there auto-triaged 98% of cases at only 92.8% accuracy. Tuning on half the test set gives honest routing numbers, at the cost of resting them on 312 images.
  2. The LLM sees six numbers, never the image. Claude Haiku 4.5 gets the label, probability, confidence, threshold, route and model version and writes two sentences. A fixed template takes over on any error, refusal, missing key or after 10 calls per session. The note adds wording, not information, which is the point: the LLM is not allowed to make clinical claims.
  3. A small ResNet18 at 64x64, trained on CPU, with the weights in the repo. The app, tests and CI run with no GPU and no dataset download. The tradeoff is low resolution and pediatric data from one center.
  4. An append-only audit log in SQLite. Every prediction and every reviewer decision is a new row, and a case's state is its latest row. It is simple to inspect and test. It is also one file shared by all visitors, with no sign-in, and not durable on the free host.

Architecture

A visitor picks or uploads an X-ray in the Streamlit app. The ResNet18 model scores it, the router compares its confidence with 0.9903 and either auto-triages the case or puts it in the review queue, and each step is written to the audit log. The summary step sends only the six output fields to Claude Haiku 4.5 on Amazon Bedrock through the US cross-Region inference profile, or uses the fixed template.

Governance and safety

  • Confidence gate: anything below 0.9903 confidence goes to a human review queue, where a reviewer confirms or overrides.
  • Append-only audit log of every prediction and review, viewable and downloadable as CSV.
  • The LLM gets six output fields and never the image; its instructions forbid findings, diagnoses and treatment advice.
  • Template fallback on any error or refusal, and a cap of 10 LLM calls per browser session.
  • Every result carries "Decision support only, not a diagnosis"; tokens and estimated cost are logged per call.
  • Secrets come only from the host's secret store, and CI scans the full git history for leaked keys.

Results

  • PneumoniaMNIST test split, 624 images: 92.1% accuracy, 99.5% pneumonia recall, 79.9% specificity, ROC AUC 0.982.
  • Routing, on the half of the test split not used to pick the threshold (312 images): 76.9% auto-triaged at 97.9% accuracy with zero missed pneumonia; 23.1% go to review.
  • Live check on 2026-11-16: one Bedrock summary, 157 input and 49 output tokens, about $0.0004.
  • 23 automated tests in CI.

Limits

Built on public research data (PneumoniaMNIST: pediatric X-rays from one center at 64x64), never used with patients, not a medical device and not reviewed by a regulator. Specificity is 79.9%, so some normal X-rays get flagged.

What I'd do in a real deployment

Train and validate on full-resolution images from the target hospitals with subgroup checks, run it in the hospital's own AWS account with sign-in, a durable audit store and role-based review, and go through clinical validation and regulatory review before any clinical use.

The problem

Teachers have grades, attendance and engagement data spread across systems and little time to read it. A student who is slipping often gets noticed late, after the pattern is already obvious.

Why I built it

I wanted to see whether a chat answer about students can be something a teacher can check: built only from the records it retrieved, showing those records, and refusing to guess when something fails. I also wanted to map what a FERPA-aware version would need in the school's own AWS account.

Key decisions

  1. Two tiers: a light hosted app and a local RAG and agents stack. The hosted chat finds records by keyword and makes one Bedrock call; LangGraph, FAISS and FastAPI stay local. There is no semantic search online, but the hosted app installs in seconds and makes exactly one model call per question.
  2. Show the sources and check the citations instead of trusting the answer. Every answer lists the records sent to the model, and any student ID it cites that was not retrieved is flagged. IDs are checked, facts are not, so a teacher still has to read.
  3. Fail closed. With no key, the cap reached or any error, the app shows the matching records and says no AI answer was generated. A broken key means no answers at all rather than a made-up one.
  4. Small, capped model use. Claude Haiku 4.5 through the US inference profile, 400 output tokens, temperature 0, 10 live calls per browser session and the cost shown per answer. Cheap and predictable, with less depth than a larger model.

Architecture

The teacher's question goes to the grounded chat, which picks matching records by keyword (named students, or the whole class sorted by topic) and sends only those records and the question to Claude Haiku 4.5 on Amazon Bedrock. The answer comes back with the records underneath, a citation check and one audit log line. The second diagram is the production design in the repo's CDK code (KMS-encrypted S3, an EventBridge-triggered ingestion Lambda, CloudWatch logs); it was never deployed and is not complete.

Production design (not deployed). Tap to enlarge

Governance and safety

  • Answers may use only the retrieved records and must cite record IDs; the records are shown under every answer.
  • A citation check flags any student ID the answer cites that was not retrieved.
  • Fail closed: no key, cap reached or any error shows records only, never generated text.
  • 10 live calls per browser session; credentials only from the host's secret store.
  • One audit log line per answer; on the free host it is wiped when the app restarts.
  • The app states it is not FERPA compliant. Built: synthetic data only, the audit log, the session cap. Not built: sign-in, a PII guardrail on each call, CloudTrail, retention rules.

Results

  • 24 automated tests pass in CI, including 13 for the grounded chat run against a fake Bedrock client.
  • Accuracy, false positives and hallucination rate have not been measured; there is no labelled evaluation set yet.

Limits

Synthetic data only: 12 student records in the hosted app with preset risk levels. Not FERPA compliant and not reviewed by any school, district or regulator.

What I'd do in a real deployment

Run it in the school's AWS account behind sign-in with role-based access, apply a Bedrock PII guardrail to every call, keep the audit log in encrypted durable storage without full student text, and measure accuracy on a labelled set before a teacher relies on it.

The problem

Legal and compliance teams sort incoming documents by type before anyone reads them for substance. It is slow, repetitive work, and a wrong label sends a document to the wrong queue.

Why I built it

I wanted to see how far a small, cheap classifier trained on public documents could go, and whether its own confidence could separate the documents it gets right from the ones a person should check, measured on agencies and courts it never saw in training.

Key decisions

  1. TF-IDF and logistic regression instead of an LLM. It trains in 43 seconds on a laptop CPU, costs nothing per document and shows the terms behind each prediction. It is weaker on documents that differ only in meaning: agency notices are right 56% of the time.
  2. Strip the giveaways before training. Headers and phrases that state the type outright are replaced with [TYPE], and tests check none remain. Scores are lower than on uncleaned text, but they measure substance, not headers.
  3. Hold out whole agencies and courts. For rules, notices and opinions the split is grouped by agency or court, so templated documents from one source can't land in both train and test. Contracts and the three presidential types come from one source each, so they are split per document.
  4. Pick the review threshold on validation and use test once. The threshold is the lowest confidence that gave 98% accuracy on auto-routed validation documents. On test the auto lane reached 96.2%, short of that target, and the README says so.

Architecture

A person pastes text, uploads a .txt or .pdf, or picks a held-out example. The classifier reads the first 6,000 characters and returns a type, a confidence, the top 3 types and the terms behind the call; documents at 0.513 confidence or above go to auto, the rest to the review queue, and every step goes to an append-only SQLite log that stores a SHA-256 of the text. Data collection and training run offline and the model file is committed, so nothing calls out at runtime and no AWS is involved.

Governance and safety

  • Confidence routing: below 0.513 a document goes to a review queue where a person confirms or corrects the type.
  • Append-only audit log of every classification and review, with a SHA-256 of the text and never the text itself (tested).
  • Leakage guard: tests check no type-announcing text survives cleaning.
  • Out-of-domain test: unrelated text (a recipe) must fall below the threshold.
  • Labelled in the app as a routing aid for document intake, not legal advice; CI scans git history for secrets.

Results

  • 432 held-out documents: 90.7% accuracy, macro F1 0.905.
  • Routing on test: 84.5% auto-routed at 96.2% accuracy; the 15.5% sent to review were right 61.2% of the time, which is why a person checks them.
  • Per class: contracts, court opinions and executive orders 100%; agency notices 56%, the weakest class.
  • 13 automated tests in CI.

Limits

Built on public documents only (Federal Register, Caselaw Access Project, CUAD), 8 types, first 6,000 characters; not legal advice and not reviewed by any regulator.

What I'd do in a real deployment

Train on the team's own intake types with reviewer corrections fed back as labels, compare against a small fine-tuned transformer, and run it behind sign-in with a durable audit store.

The problem

Card fraud teams work from alert queues. Rules are easy to explain but narrow, models catch more but are hard to explain, and both produce more alerts than a team can read.

Why I built it

I wanted to see whether a small, explainable detector could split alerts into a high-precision lane that is safe to act on and a lower-confidence lane for people, with a reason on every alert, measured on a later period it was not tuned on.

Key decisions

  1. Isolation Forest plus five plain rules, not a supervised model or an LLM. It needs no fraud labels to train, runs on a CPU, and each rule gives a sentence a person can read. Labels are still needed to calibrate and evaluate, and precision at the flag threshold is lower than rules alone.
  2. Calibrate both signals and combine them into one score. The model's percentile goes through isotonic calibration and each rule is weighted by its measured precision on validation; the two are combined as 1 - product(1 - p). Before calibration the rules added nothing.
  3. Split by time. Train on days 0 to 53, pick thresholds on days 54 to 71, test once on days 72 to 89: the way a detector meets new data in production.
  4. Two thresholds and three lanes, set from operational targets. The flag threshold keeps 80% recall and the hold threshold needs 95% precision. The cost is a review lane that is only 24.5% precise, about 62 alerts a day per 2,000 customers.

Architecture

The Streamlit app builds past-only features from the customer's own history, runs the Isolation Forest and the five rules, and combines them into one calibrated score that routes the transaction to clear, review or hold. Scores and analyst decisions go to an append-only SQLite audit log. A read-only FastMCP server gives an AI assistant the same detector over stdio; it runs locally, is not hosted, and nothing here uses AWS.

Governance and safety

  • Every flag carries a plain-language reason (tested).
  • Review queue where an analyst confirms fraud or marks the transaction legitimate; only those two actions are accepted.
  • Append-only audit log of every score and analyst decision (tested).
  • Features use only earlier transactions, so nothing leaks from the future (tested).
  • The MCP server is read-only: its scoring neither logs nor changes customer history.
  • Labelled in the app as decision support for an analyst, not a fraud determination; "hold" is a label and nothing is blocked.

Results

  • Test period (days 72 to 89, 1,318 anomalies): the hold lane is 95.4% precise and catches 60.3% of anomalies.
  • Overall 81.1% of anomalies flagged at 54.8% precision, 13.7 false positives per 1,000 normal transactions.
  • By pattern: impossible travel 100%, card testing 87.5%, velocity bursts 71.7%.
  • 23 automated tests in CI, including all six MCP tools.

Limits

Synthetic data only (328,448 generated transactions); the night rule is flattered because synthetic customers never shop between 1 and 5 am. Not a fraud decision system and not reviewed by a regulator.

What I'd do in a real deployment

Train and calibrate on the bank's own labelled history, feed analyst decisions back as labels, add merchant-level features and drift monitoring, and get model risk review before any automated hold.

The problem

Small businesses in New York miss calls they can't answer, many from callers who don't speak English, and the tools that would act on a call (calendar, CRM, payments) live in separate systems.

Why I built it

I wanted to design an AI receptionist that answers in the caller's language and acts through the business's own tools, and to work through the multi-tenant, consent and cost questions before building the telephony.

Key decisions

  1. A router in front of one Lambda per integration area. The router checks the tenant's tier and calls the agent for that tool. Failures stay isolated per vendor and tiers are easy to enforce; the cost is synchronous Lambda-to-Lambda calls that bill twice and can chain timeouts.
  2. One DynamoDB table keyed by tenant. Tenant config, call logs and consent records share one table, with TTL-based retention. Simple to run; there is no per-tenant encryption or isolation yet.
  3. Detect the language instead of translating. Comprehend finds the dominant language, with pattern matching for Yiddish and Cantonese, and the agent answers in that language. Cheaper and faster than a translation step; quality then depends on the model in each language.
  4. Separate secrets per tenant for each business's tools. Each tenant's OAuth and API tokens are their own Secrets Manager entries, referenced from the tenant's config. Clean separation, but the agent role needs broad read access to secrets.

Architecture

A call comes into Amazon Connect, which would hand tool requests to the tier-gating router Lambda, and the router calls the agent Lambdas. The voicemail agent sends audio to Amazon Transcribe and the transcript to Bedrock for a summary and urgency score, the language agent uses Comprehend, and the outbound agent places calls through Connect and schedules callbacks with EventBridge. Tenant config, logs and consent records go to DynamoDB and tokens to Secrets Manager; the Connect flows and whatever invokes the router are not written yet.

Governance and safety

  • Tools are gated by the tenant's tier; a call above the tier is refused.
  • Recording disclosure uses the stricter of the caller's and the business's state rule, in the caller's language, and writes a consent record kept for 7 years.
  • Voicemail transcripts are scored for urgency, and emergencies are flagged for a person.
  • The language log keeps only the first 100 characters of what the caller said.
  • Not built yet: CloudTrail, customer-managed KMS keys, sign-in, PII redaction, guardrails on the Bedrock call, and tests.

Results

  • No results yet: the repo has no tests or evaluations, and the cost and response-time figures in the design are targets, not measurements.

Limits

Architecture design only: not deployed, no infrastructure code, no Connect flow and no tests, and about a third of the named integrations are stubs. No real callers or data.

What I'd do in a real deployment

Write the CDK stack and Connect flows, replace Lambda-to-Lambda calls with asynchronous events, add per-tenant encryption, CloudTrail and guardrails on every Bedrock call, and test with recorded calls before any real caller.

case study

The problem

Teams putting AI on AWS rebuild the same wiring for every project: model access, tenant isolation, audit storage, model documentation. The details are easy to get wrong, like a Bedrock policy with a wildcard or a tenant ID read from the request body.

Why I built it

I wanted a small set of constructs that carry those guardrails by default, each checked by an automated test before anything is deployed.

Key decisions

  1. Grant on the caller's role instead of creating new roles. Version 1.0.0 created a role nothing used. Each construct now takes your Lambda function and grants on its role, so the permission reaches the code that calls Bedrock. The construct needs a function passed in.
  2. Scope every permission to exactly one model, endpoint or object. No anthropic.* wildcard, and the model data URL must be a literal s3:// path. Switching models means a redeploy.
  3. Fail at synth time on invalid input. Bad props stop the synth with a clear error, so mistakes show up in tests instead of in a half-deployed stack. The props are stricter as a result.
  4. Inline Python handlers, tested with fakes. No build step or asset bundling. Handlers must stay under 4,096 characters (a test enforces it), and the Stripe SDK comes from a layer you supply.

Architecture

A stack built from the library puts API Gateway, a load balancer and Cognito at the edge, with the Stripe billing functions, Streamlit on Fargate and a sign-up trigger behind them. Your own Lambda functions get scoped grants to Bedrock, a SageMaker serverless endpoint, the model registry and a KMS-encrypted bucket, while CloudTrail records object-level events and CloudWatch alarms watch for errors. Nothing here is deployed; the diagram is what the constructs synthesize.

Governance and safety

  • Least privilege by default: Bedrock access scoped to one model or inference profile, InvokeEndpoint to one endpoint.
  • Tenant isolation: the tenant ID comes only from the signed token, the app client can't write tenant, tier or plan attributes, and sign-up never overwrites an existing tenant.
  • Stripe webhooks are signature-checked and checkout accepts only allow-listed price IDs.
  • CloudTrail data-event trails with log file validation; SSE-KMS with key rotation and TLS-only bucket policies.
  • The HIPAA, FERPA and SR 26-2 modes set retention periods and tags only; they do not make a stack compliant.
  • CI scans the full git history for secrets.

Results

  • 147 Jest tests in 11 suites and 8 Python tests of the generated handlers pass (run on 2026-11-16).
  • All 9 constructs synthesize, and the packed 2.0.0 imports from a clean project with all 9 exported. 2.0.0 is published on npm.
  • Typecheck and lint pass in CI.

Limits

Tested by synthesis only and never deployed to a live account, and no project imports it yet.

What I'd do in a real deployment

Deploy each construct to a sandbox account with integration tests, add jsii builds for Python users, and adopt it in one of the other projects.
